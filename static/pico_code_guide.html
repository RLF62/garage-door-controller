Garage Pico — line-by-line guide

Firmware: 1.0.26-COMBINED-VERIFIED. This guide describes the combined firmware: fresh-reading direction verification, initial STOP/restart correction, limit handling, confirmed settings, diagnostics control and compensated vent stopping.

Confirmed startup settings

The Pico blocks movement until a complete valid set of distances and light threshold has arrived. The Zero uses saved dashboard settings, with the setup outbox as a fallback. It sends all four values with a unique settings_token. The Pico validates them before applying any, then echoes its actual values and token. The Zero retries every two seconds until they match and queries the actual values every ten seconds afterward. This detects a Pico reset even when its boot event was missed.

On the Zero, pico_settings_status.json records desired values, actual values and confirmation. No settings are written to Pico flash. Invalid candidates are rejected without partially changing values. The saved calibration remains per garage; generic defaults cannot initiate a movement at boot.

Vent stopping and settled status

This version sends the vent STOP at target minus four inches when closing, or target plus three inches when opening. These provisional leads compensate for the continued travel seen in Truck captures. After the pulse it collects fresh readings for up to 3.5 seconds. VENTED requires at least four readings spanning 700 ms, with at most 1.5 inches of spread, within three inches of the target. Movement or distance beyond the four-inch exit band clears VENTED. Failed/cached readings cannot trigger the new vent stopping threshold.

All movement requests now use several fresh readings. Only wrong initial direction is eligible for automatic correction. A later reversal after correct motion is reported as a fault, with no automatic re-close.

Diagnostic checkbox

The firmware-update page offers Enable Diagnostic Capture. Checking it enables Pico diagnostic recording and transmission, and lets the Zero save movement captures. Unchecking it disables both. Position, light, environment, heartbeat and door commands continue operating.

  1. The page saves a boolean setting through the Zero’s /diagnostics_settings endpoint into diagnostics_config.json.
  2. The serial reader checks the saved setting and sends {"diagnostics_enabled": true} or {"diagnostics_enabled": false} through the existing UART owner.
  3. The Pico’s _process_uart_line calls set_diagnostics_enabled. A mode change clears queued old diagnostic samples. The Pico replies with its applied setting.
  4. The reader records that acknowledgement in diagnostics_status.json. The page distinguishes a saved request from a confirmed Pico setting.
  5. The Zero reapplies the saved setting when the UART reconnects or the Pico announces a boot, and periodically refreshes confirmation. No flash write on the Pico is required.

The Pico starts with diagnostics disabled until the Zero supplies the setting. If the Zero has no saved setting yet, it defaults to enabling diagnostics to preserve the ongoing test workflow. Existing capture files are retained when diagnostics are disabled. Re-enable before the next test command to get a complete command capture. Old Pico firmware without this switch will not confirm the setting.

What changes when diagnostics are off?

diag_record, diag_raw, diag_result, diag_begin, diag_end, diag_pulse and diag_flush return without recording or sending diagnostic data. This removes diagnostic queueing, JSON transmission and diagnostic console output. The functions still exist and their calls perform a small enabled check. Normal sensor acquisition and dashboard messages are deliberately retained.

Door control in this version

The Pico first observes the physical door. It requires at least four fresh samples and 300 ms to classify movement, with a two-inch net change and at least two matching sample steps. Stationary evidence requires at least 650 ms within a 1.5-inch range. Samples that come from a cached failed read are not used as motion evidence.

Wrong initial motion is stopped only after re-observation. Near either limit, the controller waits for fresh stationary evidence rather than sending a STOP to an already stopped opener. After the stop is confirmed, one START begins opposite travel. The next direction is verified again. Once correct movement is confirmed, later reversal causes a fault and no automatic correction.

Fault reporting stops further automated pulses; it does not guarantee that the physical door has stopped. The opener’s own obstruction and travel-limit systems remain independent. Vent lead constants still need physical validation; the simulated run-on model is not a measurement of the installed opener.

A different queued command cancels the old motion routine and is re-observed before execution. Settings must be ready before any movement. The guide line numbers refer to this exact package; the previous versions have different line numbers.
